# V8.2 角色中心高召回感知实验

## 背景与问题

V8.1 已经证明“候选进入 Omni”与“Omni 看懂人物和动作”是两个独立问题。V8.2
因此先建立小黑三形态身份档案，并把它设为全片深看的硬门：只有黑猫、黑发儿童、
白发儿童三种形态都能通过跨镜头正例和易混淆负例的双向比较，才允许继续生成全片
候选、事件时间线和人工抽检包。

本轮实现了 V8.2 的 Prepare、Preflight、Browse、Observe Queue、Timeline、Audit 与
Evaluate 接口和 CLI，但真机运行在 Prepare 阶段发现身份能力不满足要求。用户明确
指出：体型很大的黑色兽形主体不是罗小黑。该判断被落实为源片内 hard negative，
不能仅依靠“都是黑色猫科形态”或同一动画画风合并身份。

硬原则仍为：外部知识只是 prior，源片和人工确认样例才是本片身份证据；一次不同人物
误合并比保留 uncertain 更严重。

## 候选方案

| 方案 | 思路 | 预期优劣 |
|---|---|---|
| A | 使用 `465s` 全景作为大型黑兽负例 | 首次运行方便，但该帧同时出现小黑和大型黑兽，无法确定模型比较的是哪个主体 |
| B | 改用 `445s` 只含大型黑兽的清晰近景，并继续执行全有向配对硬门 | 能排除“负例中混有小黑”的歧义；一旦仍判 `same`，可直接归因身份比较失败 |
| C | hard negative 返回 `same/uncertain` 时仍允许建档 | 可提高覆盖率，但会把已知错误人物写进全片时间线，违反 false merge 为 0 的硬门 |
| D | 加人工 ROI、强化逐图主体标签或更换模型后再比较 | 是下一轮应测方案；本轮未测，原因是先冻结当前能力基线，避免边测边改污染诊断 |

选择 B；A 的首次结果只保留为负例设计错误的审计材料，不用于证明模型能力。

典型原始错误包括：

- 5418s 对手反向比较黑发儿童时，模型把两张图都描述成黑毛、龇牙和绿灰衣服；
- 白发儿童正例对 5418s 对手时，多次只根据相同工地背景、吊车和动画画风返回
  `same`。

模型原始响应还出现 `.com`、重复 `Assistant` 和尾随文本。解析器成功取出了第一个

重写本次实验结果。

## 诊断依据

排查链如下：

1. 首次使用 465s 负例时，模型将其与黑猫正例判为同一主体；人工复查发现该全景同时
   含有小黑和大型黑兽，因此该证据无法区分“模型认错”和“模型看到了画面里的小黑”。
2. 改用 445s 独立近景后，画面只含大型黑兽，没有小黑；同样的 6 个有向负例比较仍
   全部返回 `same`。
3. 黑发和白发形态也在清晰的人形—大型对手比较中出现 3 次和 5 次错误合并，说明问题
   不只发生在“两个黑色猫科主体”这一对难例。
4. 所有正例间比较都通过，但 hard negative 大量失败，表明模型能识别粗类别、相同场景
   和画风，却不能可靠完成本任务要求的“同一具体人物”判定。

第 2 步排除了负例混入目标人物这一假设；第 3、4 步把问题进一步定位到跨图主体锚定与
个体身份比较，而不是全片候选召回、FlashVID 压缩或事件 Planner。由于失败发生在
FlashVID Browse 之前，本轮没有证据评价后续浏览召回能力。

## 选择与理由

保持严格阻断，不降低 hard-negative 门槛，也不把 `same` 人工改写成 `different`。
V8.2 的目的正是先确认 Omni 是否具有局部理解和身份区分能力；若在三张清晰正例和一张
清晰负例上仍大量误合并，扩大到全片只会生成更多看似完整但身份错误的事件。

同时保留以下修正：

- 445s 及同段大型兽形帧进入黑猫形态 `invalid_source_times_s`；
- 5418s 深色大型对手继续作为两个人形的 hard negative；
- V8.2 只有 profile `ready` 才能建立 search card 和进入 Preflight；
- 下一轮 profile 比较采用进程池批量提交，避免八卡加载后串行推理。

未采用方案 C，因为覆盖率不能以错误身份为代价。方案 D 尚未实测，下一轮应在同一冻结
样例上比较“全帧”与“全帧 + 明确配对 ROI”，并禁止把背景、画风、同物种或同颜色单独
作为个体身份依据；仍不引入 YOLO、Tracker 或专用 ReID。

## 验证

本轮解决判定标准不是“代码能跑”，而是三种形态均满足：正例双向全部 `same`，所有
hard negative 与正例双向全部 `different`。实际三个形态均为 `conflict`，因此问题
**未解决**，但阻断机制正确工作：

- `decision=FAIL`；
- `failure_class=verification`；
- `failure_stage=prepare`；
- `reason_code=three_human_confirmed_forms_not_usable`；
- 未启动全片 Omni 深看；
- 未生成自动小黑事件时间线或任何视频。

首次歧义负例产物保存在服务器
`target_profile/attempt_001_ambiguous_negative/`，第二次干净负例结果保存在正式
`target_profile/char_xiaohei/`。两次产物没有互相冒充。

残留风险：本轮没有加入人工 ROI，因此尚不能判断错误主要来自模型本身、多图输入中的
主体定位，还是当前 prompt 对“同一具体个体”约束不足；也没有比较其他视觉模型。并发
修复只做了本地自动测试，尚未进行下一次服务器计时对照。这些未测项不能解释成已修复。

## 结果

V8.2 真机实验在正确的最早故障层停止：三形态身份档案 `usable_form_count=0`、
`conflict_form_count=3`，Prepare 阶段 FAIL。大型黑兽没有被写入小黑的正式档案，失败
结果也没有扩散到全片候选和事件时间线。

当前结论不是“小黑在电影里找不到”，而是：**现有 Omni 多图身份比较无法可靠地区分
小黑与清晰 hard negative，尚不具备作为全片身份门控器的能力。**

## 从结果学到什么

1. hard negative 必须只包含被否定主体；负例画面同时含有目标时，模型判 `same` 没有
   诊断价值。
2. “同为黑色猫科、同一动画画风、同一背景”只能证明视觉类别或场景相近，不能证明是
   同一人物。身份 validator 应拒绝只基于这些理由的 `same`。
3. 正例全过、负例大量失败不是高身份准确率，而是模型倾向宽松合并。必须分别报告
   positive consistency 与 hard-negative false merge。
4. 在全片高召回之前先做小型能力预检是正确的：本轮只花 36 次比较就阻止了数百次
   不可靠深看和错误时间线。
5. 资源池“加载四个 worker”不等于任务并发；调用方必须批量提交，GPU 利用率才会真实
   提升。
6. 下一轮只应修改身份输入与判断契约，在同一冻结样例上做 A/B；通过前不得恢复 Browse、
   Timeline、Planner 或 Renderer。
