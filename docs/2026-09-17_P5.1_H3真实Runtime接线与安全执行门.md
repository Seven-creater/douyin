# P5.1：H3 真实 Runtime 接线与安全执行门

> 阶段结论：**CPU 接线通过，真实能力仍未验证**。本轮没有启动 H3、Omni 或 GPU 推理，没有执行服务器 `git pull`。本地 dry-run 的 S0–S7 均为 `unverified`；P5 Gate A（真实 V9 人工冻结）和 Gate B（真实 H3 条件效果）仍未完成。

## 背景与问题

P5 的只读检查发现八张 GPU 当时均被他人任务占用；即使资源释放，`reference-generate-v9g --phase capability` 也只有 `--plan-only`，无法提交、轮询、下载真实 S0–S7 任务。P4 已有 Condition Manifest、资产 SHA、能力 Registry、假后端和媒体规格检查，但这些只证明本地计划，不证明真实 H3 请求送达或条件生效。用户拍板 P5.1 **仅补 CPU Runtime 与安全门**，不进入 P6、Repair 或真实模型实验。

代码地图（改动前的职责与本轮接线）：

| 环节 | 现有或本轮位置 | 状态 |
|---|---|---|
| CLI | `src/agentic_video/cli.py` | 原仅 plan-only；新增 dry-run、sync-check、三门后 execute |
| Request Compiler / Manifest | `src/agentic_video/generation_p4.py` | 复用条件顺序、标签、SHA 和能力需求，不重编译 |
| HTTP Adapter | `src/agentic_video/generation_v9g.py` 的 `SGLangH3Client` | 复用官方 JSON `/v1/videos`，拆出 submit/poll/download |

| 旧接口 | `src/generation/minimax_client.py`、`minimax_serve.py` | 旧 `/generate` 未作为正式 capability 后备路径 |

当前 [SGLang H3 cookbook](https://github.com/sgl-project/sglang/blob/main/docs/cookbook/diffusion/MiniMax/MiniMax-H3.mdx) 使用带有有序 `conditions` 和服务端可见 `file://` URI 的 JSON 请求；它不是 multipart 上传。本轮审计因此锁定 JSON 请求体字节、条件位置和源文件 SHA，而不虚构 multipart 字段。若官方服务不返回实际接收清单，客户端 receipt 只能证明**发出了什么**，不能单独证明模型用了什么。

| C | 复用已有 SGLang 客户端，接入 P4 审计和 mock HTTP，执行前强制 P0/代码/GPU 门 | 能先验证请求 plumbing，且不声称条件效果；用户拍板采用。 |

## 实测/对比

本地合成夹具包含不同颜色的首帧、尾帧、身份图、4 秒视频和 WAV；只用于协议测试，不代表 H3 生成质量。mock HTTP 实际接收 `POST /v1/videos`，再模拟轮询与媒体下载。

| 检查 | 观测结果 | 系统结论 |
|---|---|---|
| 正常 S7 image + first-frame | 发送的 JSON 请求体 SHA 与客户端审计 SHA 相同，条件顺序保留；下载的合成 MP4 可探测/解码 | `backend_transport_ok=true`，effect 仍 `unverified` |
| S5 服务端 receipt 丢弃 video | 服务端 `accepted_conditions` 与请求不一致 | `request_delivery_mismatch` |
| 两张不同图片的顺序被交换 | receipt 与 Manifest 顺序不一致 | `request_delivery_mismatch` |
| S0 完成但下载损坏内容 | `ffprobe`/解码失败 | `transport_failed`，不算生成语义失败 |
| S0 持续 running | 超时 | `poll_failed`，归类 infrastructure |
| 后端失败 / 下载 503 | 分别注入 | `backend_failed` / `download_failed` |
| `--dry-run-real-backend` | 输出 S0–S7 的真实协议请求、Manifest、资产和客户端 receipt | 8 案、**0 次 HTTP 请求**、Registry 全部 `unverified` |

## 诊断依据

首先，旧 `--plan-only` 能生成 Manifest，但没有任何真实任务状态或下载结果，所以“计划完整”不能解决 P5 的执行缺口。其次，mock 正常返回 MP4 后 effect 仍为 `unverified`，排除了“HTTP 200 / 可解码 MP4 等于条件生效”的错误归因。对抗模式在 request receipt、轮询、下载和解码的不同层分别失败，说明错误没有被统一误记为 `conditioning_ineffective`。

测试中曾把两张图片都指向同一文件，服务端交换顺序仍得 `unverified`。原因是两个 condition 在序列化后完全相同；改成不同图片后，换序被 `request_delivery_mismatch` 检出。另一次真实只读 sync-check 正确写出计划，却因返回字典顶层 `status` 与 CLI 状态输出参数冲突而退出 1；将服务器状态嵌套为 `server_sync_plan.status` 后重跑，命令退出 0，仍未执行 pull。这两个失败都进入了回归测试。

分阶段执行也有缓存风险：S0–S3 与 S4–S7 可能在不同时间运行。现在用 `capability_run_identity.json` 绑定代码 SHA、各案请求 SHA、端点和资产 SHA；不一致时阻断合并。Canonical Registry 只在八案各有成功 transport 证据、无 mock、无执行失败且身份一致时原子提交；中断只写 proposed，不覆盖 canonical。

## 选择与理由

采用方案 C。P4 Manifest 是条件真值，HTTP 层只按原顺序序列化；真实请求体与审计使用同一组字节。Runtime 只负责 submit → poll → download → transport，不在客户端把 `completed` 推断为 `effective`。效果检查保留 deterministic / model judge / human 接口，但无真实证据时保持 `unverified`。服务器同步只读判定 `SAFE_TO_FF_PULL / BEHIND_SAFE / BLOCKED_* / DIVERGED`，不自动修复工作区。真实 `--execute` 在任何 POST 前要求已冻结 P0、匹配的干净运行 checkout 和可用 GPU 集；许可证门仍沿用 V9-G 既有硬门。

## 验证

阶段验收标准为：S0–S7 的真实协议请求可在无网络 dry-run 中审计；mock HTTP 能分辨正常、丢条件、换序、损坏文件、超时和下载/后端失败；未冻结 P0、忙 GPU、旧/脏 checkout 会在提交前阻断；fake/mock 不得使 Registry `effective`。上述 CPU 标准已由 694 项全量测试、23 项专项测试及真实 dry-run 命令满足。

未验证：真实 SGLang/H3 版本与服务返回格式、服务器端 `file://` 可见性、H3 是否使用条件、真实媒体质量、真实 GPU 占用时的 live gate、Omni/人工 effect 评分。当前许可证门仍未获人工通过，P0 三个 Program 仍未人工签署冻结；所以**真实 `--execute` 未运行，也不应运行**。

## 结果

已推送代码提交 `810f6c1`（Runtime 与测试）和 `af05a7a`（只读 sync-check CLI 修复）。本地 CPU 产物位于 `data/agentic_runs/p51_cpu_20260917/`：八案 dry-run 请求、全 `unverified` Registry 和服务器只读同步计划。未启动或干扰服务器上的 H3、Omni、GPU 任务；未修改服务器工作区，未删除两个未跟踪文件。P5 Gate A/B 仍为未完成，本轮没有生成视频或能力有效性结论。

## 从结果学到什么

Protocol plumbing、媒体传输与条件效果是三个独立结论；只有带真实效果证据的逐项验证才能提升能力状态。分阶段冒烟必须绑定整次运行的代码、端点和夹具，否则八个单案的“完成”可能来自不同实验。下一步不是扩 Repair/P6，而是等待安全资源与人工许可：重新只读检查服务器和 GPU → 人工通过许可证门 → 真实 V9 三 Program 逐段审核并冻结 → 再按 S0–S7 逐案验证。每一步未 PASS 时停止，不把本轮 mock 结果带入真实能力 Registry。
