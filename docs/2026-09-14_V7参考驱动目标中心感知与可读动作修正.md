# 2026-09-14 V7 参考驱动目标中心感知与可读动作修正

## 背景与问题

V7 的研究目标是：不使用 YOLO、Ultralytics、Tracker 或专用 ReID，以源片
`5385–5460s` 为唯一搜索范围，围绕可信视觉锚点 S0，经过参考片分析、TargetAlbum、
FlashVID 多预算浏览和 Omni 核验，剪出“S0 受压 → 主动行动 → 结果”的参考驱动短片。

第一版设计已经把 `observation_interval`、`core_interval` 和 `renderable_interval` 分开，
但编辑策略仍容易把“逐帧找到动作核心”误解成“最终只播放动作核心”。用户指出：关键帧
用于找到精确切点，不等于观众只需要看到几帧；成片必须保留理解动作所需的准备、发生和
反应，且不能再用统一的 0.15–2 秒、4 秒或最低刀数硬约束代替内容判断。

因此本次不是重做 V7，也不扩大到全片扫描，而是进行范围受控的增量修正：

- 新增编辑策略版本 `readable_highlights_v1`；
- 最终展示区间必须包含 core，并位于已核验 observation 内；
- Planner 显式记录最终源片区间、前后文及保留理由；
- 正常速度逐段复看后才能渲染，最终成片仍需独立 blind review；
- 上游输入不变时复用 ReferenceTask、TargetAlbum 和 A/B/C/D browse 结果；
- 使用独立目录 `lxh_v7_target_20260914_readable_highlights_v1`，不覆盖原始 V7 run。

## 候选方案

| 方案 | 思路 | 预期优劣 |
|---|---|---|
| A：core 直接作为成片区间 | 逐帧定界后只播放最小证明片段 | 最短，但会把定位精度误当成观看时长，容易只剩结果帧或动作残片 |
| B：固定给 core 前后各加常数 | 例如统一增加 0.5 秒 | 简单，但镜头切换、动作速度和语义完整度不同，固定 padding 可能跨入别的人物或镜头 |
| C：使用完整已核验 observation | core 定位重点，observation 保留可读上下文 | 本轮选用的保守起点；能避免 core-only，但 observation 若本身跨镜头，仍可能带入错误内容 |
| D：Planner 单独选择 final display interval，并对该区间正常速度复看 | 把观察、证明和最终展示作为三个独立决策 | 目标架构；审计最完整，但要求 evidence 的 observation 本身可靠，且复看不能替代全片盲审 |
| E：修改 seed、身份协议或重新全量浏览 | 从上游重新寻找干净主体与证据 | 可能解决本轮真实首个故障，但超出此次“只修播放可读性”的范围，未实施 |

最终实现采用 C 作为当前 Evidence v3 的安全默认，并落地 D 所需的数据合同和复看门控：
`final_source_interval`、`context_padding`、`selection_reason`、策略版本和有序区间共同进入
计划及缓存键。没有引入新检测器、新模型、全片扫描或额外故事 critic。

## 实测对比

### 代码与接口修正

代码提交 `ec268d9` 修改了 `cli.py`、`evidence_pipeline.py`、`evidence_units.py`、
`renderer.py`、`target_v7.py` 和 `tests/test_target_v7.py`，主要变化如下：

- `EvidenceUnitV3` 要求 `renderable_interval` 完整位于 `observation_interval` 内并覆盖
  `core_interval`；
- 自动 Evidence 不再用 `core ± 0.15s` 生成展示区间，而是保守继承已核验 action
  observation，并记录来源；
- Edit Plan 升级为 `reference_driven_edit_plan_v2`，每段同时记录 observation、core、
  render 和 `final_source_interval`；
- 移除 Renderer 的 0.15 秒通用最短片段限制，不设最低刀数，不为参考时长补 filler；
- 超过参考片 shot P90 只要求写明语义完整理由，不再直接裁掉；
- 渲染前用同一个 Omni runner 正常速度复看每个最终片段，检查动作变化、过短、冗余、
  主体关系和可证明结果；
- Content Master 缓存使用策略版本、有序 Evidence、最终源区间和时长计算计划哈希，
  防止策略改变后复用旧视频；
- Blind review 增加 `too_short_intervals`、`redundant_intervals`、
  `subject_relation_clear`、`supported_result` 和 `unsupported_claims`；
- 自动 Arm 失败不再阻止 Oracle Arm 运行，便于隔离 browsing/mining 与 planner/renderer。

### 身份册对照

Held-out GT 从未进入 TargetAlbum prompt，但结果发现两次 hard-negative 错误合并和一次

| 时间 | 模型判断 | Held-out GT | 结果 |
|---:|---|---|---|
| 5390.5s | same | different | hard-negative false merge |
| 5389.5s | same | different | hard-negative false merge |

人工检查实际帧后发现，用户原计划指定的精确 seed `5391.5s` 落在叠化/转场附近，画面
同时包含白发儿童叠影与目标深色头发主体，不是干净身份锚点。由此可解释模型为什么把相邻

本次新改的播放长度策略。

## 选择与理由

选择“core 负责证明、final display 负责观看”的三层区间合同，并为 V7 单独版本化为
`readable_highlights_v1`。理由是：动作边界越精确，越不应该让它顺便决定观众所需的
上下文；语义完整是硬要求，参考片时长和 shot P90 只应提供风格偏好。

本轮没有自动裁掉盲审暴露的跨人物画面。因为 segment_01 的 Oracle core 自己跨过镜头，
直接改 `final_source_interval` 会同时改写证据含义，违反“先核验证据、后决定展示”的
职责边界。正确处理是保留当前 blocked 产物，下一轮以新的 Evidence/Oracle 版本重新
核验这些局部区间，而不是覆盖历史 JSON。

同理，没有为了让实验通过而更换 seed 或重建 TargetAlbum。seed 位于叠化帧是当前实验
首次故障的关键事实；修复身份 anchor 属于下一项独立变量，若与播放长度修正混在同一轮，
就无法判断成功究竟来自哪一项修改。

## 从结果学到什么

1. “关键帧找准核心”与“成片播放多久”必须是两个决策；本次 1.92–2.75 秒片段比直接
   播 core 更可读，说明此次增量修正方向成立。
2. observation 是模型理解动作时看的范围，不保证范围内每一帧都属于同一主体或同一
   可用镜头；最终 display 仍需检测切点和局部复核。
3. 逐段 reviewer 能判断局部动作完整，却可能看不出三段拼接后的跨人物关系；因此逐段
   复看不能替代无计划上下文的终片 blind review。
4. 精确到一个时间点的可信 seed 仍需要“干净帧质量门”。`5391.5s` 落在叠化帧，使后续
   双向身份比较建立在歧义锚点上；下一轮应保留用户指定语义位置，但从邻近原生帧选择无
   叠化、主体清晰的 anchor，并把选择过程和 SHA-256 写入审计。
5. A/B/C/D 同为 0.40 recall 不意味着最低成本 A 已经足够；当四组都低于目标时，结论
   应是浏览/身份条件共同不足，而不是“压缩无损”。
6. Oracle Bank 可以隔离自动浏览，但 Oracle 时间标注也不是天然真值。原 Oracle core
   跨镜头时必须派生新版本并重新 identity/action/relation/boundary 核验，不能手工静默
   修边。
7. 同画面双音频仍可能让模型给出差异很大的故事复述。逐帧相同只证明渲染控制实验干净，
   不证明编辑表达已经稳定。
8. 本轮最早故障仍在 identity，随后才是 browsing，再后才是成片表达。可读动作策略已
   落地，但只有先修干净 seed 和 Evidence 边界，才能有效评价它对最终短片的真实增益。
