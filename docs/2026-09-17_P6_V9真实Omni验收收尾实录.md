## 诊断依据

两个 bug 的定位链都由**原始响应文件**直接坐实，不靠猜：

1. **retry5 edit 截断**：`raw_responses/edit_program.txt` 尾部是数百个 `0.1, 0.1, ...`——
   模型在自报 measured_style 的 `shot_duration_distribution` 数组，撑到 4096 token 上限被截，
   解析器在截断点报 `Expecting ',' delimiter`。改 prompt 删字段后该现象消失。
2. **content 契约字段缺失**：看 retry5 目录新生成的 reference_content_program.json——
   `perception_focus.primary_focus` 模型输出字符串 `"subject"`（prompt 示范写的是
   `{"type": "subject|..."}`，读起来像类型标注）；`continuity_basis` 模型只填 `subject` 一键
   （prompt 示范恰好只给了 subject 一个键），而校验器（validate_reference_programs）要求
   六维度**全部**有 reason、required/preferred 还要 evidence_ids。
   **prompt 示范的最小样例被模型逐字照抄**——示范欠指定，不是模型偷懒。
3. 附带发现：evidence 缓存键含 `builder_sha256`（本文件自身 SHA，
   reference_program_v9.py:405）——任何一行改动都会击穿全链缓存。这是"改构建器即全量重验"
   的刻意设计，代价是本轮两次提交各烧一次全量 GPU（~13min×2，卡 0,1 空闲可接受）。

## 选择与理由

选 B（改 prompt 补全示范 + 全量重跑）。修 prompt 而不是放宽校验器：校验器要求的是
诚实契约（每个连续性判断都要画面依据，防"填表通过"），缺的是 prompt 把契约说全。
与 7fd1137/8eb61d7/adfa9d5/f45fe54/42632c6 一脉相承：修法=补全示范+显式规则+回归测试锚定。

## 从结果学到什么

1. **prompt 里的 schema 示例就是模型的输出上限**：示范给一个键模型就填一个键，示范写成
   类型标注模型就照抄类型值。凡校验器要求的字段，示范必须给全量键集 + 显式规则句，
   并用回归测试把"prompt 含全部维度"钉死（防止未来改 prompt 时静默退化）。
2. **让模型自报任何"程序可计算"的统计都是纯风险**：measured_style 数组既浪费 token（截断）
   又必然被程序值覆盖。凡是能从确定性证据（PTS/ffprobe）算出的字段一律程序算。
3. **缓存键含 builder_sha 的设计要配合"少改这个文件"的纪律**，或未来把 prompt 拆到独立
   常量文件（prompt 文件 sha 进键、逻辑文件 sha 不进），否则每次措辞修复都是一次全量 GPU 重验。
4. 服务器同步的 GitHub 通道（gh-proxy）当天不可用，server 直推通道（push from_local + ff-only）
   零成本接管——双通道冗余再次证明必要。
