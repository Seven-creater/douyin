# 2026-09-08 写盘目录缺失四连崩（analyze_editing）

## 背景与问题

`analyze_editing`（Omni 反推剪辑手法）服务器首跑：6 条模板逐条分析，链路日志显示
4 条"分析完成"，但产物 `result.json` 一份都没有。每条 Omni 推理 3-5 分钟 GPU 成本，
4 连崩 ≈ 20 分钟 GPU 白跑。

## 候选方案（排查时的假设）

| 假设 | 验证 | 结论 |
|---|---|---|
| Omni 推理本身崩（OOM/输入） | 日志：模型加载正常、decord 读帧正常、每条都跑满全程 | 推翻 |
| done_or_skip 误判跳过 | 产物目录根本不存在，无从跳过 | 推翻 |
| **写盘失败** | Traceback 直指 `write_result_json → FileNotFoundError: .../analysis/result.json.tmp` | **确认** |

## 根因

`common.write_result_json` **不创建父目录**（感知工具的隐含约定：目录由调用方建）。
`src/template/extract_template` 等老调用方都有 `tool_dir_for()` 先建目录的习惯，
新写的 `run_analysis` 直接传了 `tdir` 没建 → tmp 文件写入即 FileNotFoundError。
且 CLI main 的 `except` 吞掉异常只打日志，链路脚本 `||` 判退出码继续跑下一条，
于是**同一错误静默重复 4 次**。

## 验证

补跑链重跑后以**产物文件数**为判定（`ls data/library/editing/*/analysis/result.json | wc -l`
从 0 → 6），而非流程日志；每份 JSON 人工抽查 mode 字段与 timeline 条数。残留风险：
partial 模式的记录（时间戳告警未过校验）单独标注，不与 json 混计。

## 选择与理由（修复方式）

调用方写盘前 `tdir.mkdir(parents=True, exist_ok=True)`（`b20ebd8`）。
备选：改 `write_result_json` 内部建目录——更彻底但动公共件，感知层 8 个调用方
行为面广，V0 期间选最小改动；后续再统一收口。

## 结果

- 修复部署后，链内最后一条自动用新代码成功，前 5 条补跑链重跑全部落盘；
- 损失：4 次 Omni 推理（~20min GPU）+ 一轮人工排查。

## 从结果学到什么

1. **"跑完了"≠"产出了"**：链路脚本的"分析完成"日志只代表进程退出码 0 路径之外
   被 `||` 兜住了——监控应该盯**产物文件数**而不是流程日志（本次监视器字段
   `分析完成数=0` 恰好是唯一诚实指标）；
2. 公共工具的隐含约定（谁建目录）要有防御：要么 write 侧 `mkdir`，要么每个新调用方
   review 时查这一条——这次属于后者没做；
3. 长链任务第一步先用 1 条**人工验产物**再放量，四连崩本可在第一条就止住。
