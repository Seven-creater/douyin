# v4 Run A 死循环根因修复与 A-v3 全绿（2026-09-20）

## 问题

Run A-v2（共享 schema + no-progress 注入版）陷入无限循环：
`extract_assets FAIL → inspect → repair_screenplay → FAIL → …`
直到人工 kill。表面症状是"validator 互相打架"，实际是**三个问题叠加**。

## 根因（三叠加）

### 根因 1：双权威矛盾（已知层）

deterministic schema 校验说 character 的 immutable 必含
identity/face/body_build；通过后再跑 Omni 语义验收，Omni 又按自己的
理解判"immutable 不该有这些"→ 下游 FAIL。修好必挂、挂了必修，
永无 PASS 路径。

**修复**：`validators/__init__.py` 的 `test_asset_graph` 只跑
`skills/asset_schema.py::validate_asset_graph`（确定性 schema 唯一
权威），Omni 语义层整个删除。

### 根因 2：Skill prompt 自教错误（隐藏层）

`EXTRACT_ASSETS_PROMPT` 示例里写着 `"status": "deferred_to_M4"`，
而 schema 要求 `status ∈ active|deferred`——**prompt 自己在教模型输出
必挂的格式**；且示例缺 `schema_version` 字段。模型照示例写 → 必挂。

**修复**：prompt 原生内嵌共享 `ASSET_GRAPH_FORMAT_SPEC`（不再靠
运行脚本 monkey-patch 注入），显式禁止 `deferred_to_M4` 类值和外层
包装。

### 根因 3：修复动作打错靶（行为层）

asset_graph 挂的是 graph 格式，Agent 却反复 repair_screenplay
（screenplay 根本没错）——因为 extract_assets 不接收失败反馈，
re-extract 与首次 extract 无差别，Agent 在可用动作里找不到正确的
修复动作，只能乱打。

**修复**：extract_assets 接收 `test_failures`，schema 失败明细直接
注入 re-extract prompt——re-extract 成为 asset_graph 的合法修复动作。

### 顺带基建修复

- **镜像包装穿透**：repair 的 payload 包了 `{"screenplay": ...}`，
  Omni 照抄外层结构原样返回，`write_draft` 存进嵌套壳 → `_unwrap`
  解包（多个候选键）。
- **NoProgressDetector 漂移**：detector 在运行脚本里挂在
  `agent_loop(max_steps=1)` 外面，从未真正生效 → 原生集成进
  `agent_loop`（`no_progress_detector` 参数），停滞 break 并输出
  `stop_reason`。
- **restricted_actions 幻影技能**：列表里有不存在的
  `repair_asset_graph` → 改为真实 M1 技能名。

## 方案对比

| 方案 | 结果 |
|---|---|
| 只修根因 1（删 Omni 语义层） | prompt 仍教错格式（根因 2），仍会挂 |
| 只修 1+2 | 挂了之后 Agent 仍乱修 screenplay（根因 3），仍绕圈 |
| 1+2+3 全修 | A-v3 三步全绿，零修复循环 |
