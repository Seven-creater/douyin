## 背景与问题

P4 已通过 CPU/假后端检查，但不能证明真实 V9 Program 可被人工冻结，也不能证明 H3 的首尾帧、图像、视频或音频条件真实生效。用户拍板将 P5 分成 Gate A（真实 V9 理解与人工冻结）和 Gate B（真实 H3 S0–S7 条件效果），禁止直接进入 Generation Unit Pilot、Repair 或完整视频。既有规则要求共享服务器仅使用真正空闲的 GPU，不终止或抢占他人任务。

## 诊断依据

第一层阻断是资源：所有八张卡都在运行其他人的计算任务，不存在可安全选用的 GPU。第二层是版本与状态：服务器代码还没有 P4 的最新门控，且其工作树存在未跟踪文件，不满足本计划要求的“HEAD 对齐、工作树干净”。第三层是接口真实性：当前 CLI 的 `reference-generate-v9g --phase capability` 非 `--plan-only` 路径明确抛错；P4 只提供计划与假后端检查，没有接入真实 S0–S7 效果评估。即使 GPU 明天空闲，也不能把旧 `probe_h3_capabilities` 的媒体传输成功升级为 `effective`。

这些是独立障碍；本轮首先因 GPU 占用停止，所以没有让服务器更新代码，也没有运行 Gate A 或越过 Gate A 尝试 Gate B。

## 选择与理由

选择 C。遵守“别人正在用就停”的用户要求，并严格维持 Gate A → Gate B 顺序。没有为了得到“结果”而复用旧 fixture、旧人工审核表、P4 fake 输出或未绑定本片 SHA 的 Program。执行清单明确写出未采取的动作，命令预览只作为下一次资源可用时的操作顺序，不暗示已执行。

## 验证

已验证：SSH 可只读访问；源片本地/远端 SHA 相同；服务器代码与工作树现状；GPU 利用率、显存和占用 PID；当前 CLI 的真实 capability 路径尚未接入。P5-A/B 的任何模型质量指标均**未测**。本轮没有生成 `reference_content_program.json`、`reference_edit_program.json`、`material_requirements.json` 的真实新版本，也没有 `capability_registry_after.json` 的真实能力升级。

解除本次阻断需重新检查 GPU，而不是沿用本次快照；服务器同步前须保留并明确处理现有未跟踪文件；Gate A 必须先由真实运行与逐 Section 人工审核取得 frozen SHA；Gate B 还需真实请求、媒体和条件效果证据的执行路径。三者缺一不可。

## 结果

P5 状态为 **BLOCKED_BY_GPU_AVAILABILITY**；Gate A 和 Gate B 均未开始，S0–S7 全部保持 `unverified`。未运行 H3、Omni、GPU 任务、Program accept/freeze、正式 Unit 或 Repair。没有可报告的生成质量或条件有效性结果。

## 从结果学到什么

“代码门控已写好”与“真实模型能力已验证”必须分开报告。共享资源占用应阻断模型实验，而不是作为调整阈值或退化成假运行的理由；版本、人工冻结和真实效果评估也是彼此独立的放行条件。下一次 P5 只能从新的资源与输入检查开始，不能把本次 preflight 当作 Gate A/B PASS。
