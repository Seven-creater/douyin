# 2026-09-08 素材检索架构选型（镜头怎么被"找到"）

## 背景与问题

素材库需要回答"这段故事需要 XX 画面 → 库里哪个镜头匹配"。几小时正片/几百镜头
不可能让大模型直看（visual token 爆炸 + 14 tok/s 输出瓶颈，Phase 2 已实测 92.6s
高密度混剪即爆预算），必须建**分层外置记忆**：确定性工具打底，模型只看候选。

## 候选方案

| 方案 | 思路 | 预期优劣 |
|---|---|---|
| A. CLIP 图文检索 | 查询文本→CLIP 文编码 vs 关键帧图编码 | 快、成熟；中文/细粒度动作弱，命中不可解释 |
| B. VLM 看画面→结构化中文描述→E5 文本语义检索 | Qwen2-VL 给每镜头写「主体/动作/场景/情绪」；查询与描述同语言同结构比 cosine | 可解释（命中理由就是文字）；语义粒度高；多一次 VLM 批量成本 |
| C. 大模型直看全库 | 每次检索都让 Omni 看素材 | 不可行（token/速度，见背景） |

## 实测/对比

- C 直接排除（预算实测依据见 Phase 2 omni_full 成本：166.9s/条均值、92.6s 混剪爆输出预算）。
- A vs B 未做 A/B 数据对比——**用户拍板选 B**（理由：可解释、可控；CLIP ViT-L 文本侧
  是英文且对"摘面具特写震惊"这类细粒度动作查询弱）。A 的代码（ClipIndexer）保留在
  git 历史（1c5b0a6 前），随时可拉回来做对照实验。
- B 落地实测（进行中）：Qwen2-VL-7B（服务器自有，16G 单卡）56s 加载，**~3.5s/镜头**，
  593 镜头全库约 35 分钟一次性成本；E5-Omni-7B（sentence-transformers 5.4 原生支持）
  做文本嵌入，索引/查询各秒级。

## 选择与理由

**B**。检索质量的上限取决于描述质量而非匹配算法；描述是结构化中文，查询由故事板
LLM 生成同构句子（"主体：…；动作：…；场景：…"），语义对齐天然好。代价是入库时
多一遍 VLM 批量（一次性），换来每次检索零 GPU 大模型成本 + 命中可审计。
