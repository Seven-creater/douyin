# 2026-09-14 V6 证据中心微剪与八卡并发

## 背景与问题

V5/V5.1 已能在 `luoxiaohei1` 的 `2965–3005s` 内定位、保留对白并生成双音频
版本，但输出仍接近“截取一段原片”。用户用参考视频指出：短视频不必完整搬运长事件，
而应使用 0.15–2 秒短片或关键帧，快速堆叠“困境、能力、反转、结果”等视觉证据。

因此本轮不扩大到 72 窗，也不先假定 token 或覆盖率不足。用户拍板采用：

- 首轮仍固定 w15：`2965–3005s`；
- Evidence Unit 同时支持视频微片段和关键帧；
- 参考视频使用本地 `data/videos/7682719919410072847/video.mp4`；
- 服务器夜间允许使用全部 8 张 A6000，高并发运行。

真正需要验证的是：同一个 40 秒连续镜头能否被拆成可编辑的最小证据，而不是再次变成
一个粗 Event 或一整段 utterance。

## 候选方案

| 决策点 | 方案 | 预期优劣 |
|---|---|---|
| 素材表示 | 继续复用 Event/utterance | 改动小，但只能得到长片段拼接，无法表达“一帧或 0.5 秒就是证据” |
| 素材表示 | 新增 Evidence Unit | 多一层结构，但事实位置与编辑选择职责清晰，可直接驱动微蒙太奇 |
| 长镜头分析 | 一个真实 shot 调一次 Omni | 调用少，但 w15 的 40 秒 oner 仍会得到粗摘要 |
| 长镜头分析 | 最多 6 秒一块、相邻重叠 0.5 秒 | 调用增加到 8 次，但能看到跨边界动作，并可对重复证据去重 |
| 8 卡使用 | 一个 Omni 实例跨 8 卡 | 实现简单，但此模型两卡已能容纳；额外卡不形成请求并发 |
| 8 卡使用 | 8 个单卡实例 | 并发高，但 30B thinker 约 69GB，单张 48GB A6000 无法容纳 |
| 8 卡使用 | 4 个常驻实例，每实例 2 卡 | 选用；`0,1 / 2,3 / 4,5 / 6,7` 四路并发，兼顾显存与吞吐 |
| 双音频 | 两次独立渲染画面 | 容易出现帧差异，无法形成干净控制实验 |
| 双音频 | 一次 Content Master，视频流 copy 后只改音频 | 选用；逐解码帧 checksum 必须一致 |
| 发布 | 自动盲验通过即生成 `rendered.mp4` | 省一步，但模型自报不能替代人工理解 |
| 发布 | 自动通过后仍 `human_acceptance_pending` | 选用；人工确认前根目录正式文件不存在 |

相关研究只作为架构旁证，不替代本仓库实测：HIVE 将自动编辑拆为 highlight、开头/
结尾选择与 pruning；Video Moment Montage 关注细粒度 moment 检索与组合。两者均支持
“剪辑单位应细于完整事件”的方向，但没有证明本项目 w15 一定能产出合格证据。

## 实测/对比

### 参考视频阈值

本地真实参考视频时长 `21.933s`。对同一文件运行 scene detection：

| scene threshold | 检出 shot 数 |
|---:|---:|
| 0.30 | 1 |
| 0.20 | 7 |
| 0.15 | 9 |
| 0.10 | 12 |
| 0.05 | 16 |

`0.30` 会把参考短视频错误看成一镜到底；`0.05` 更容易把画面运动当切换。最终采用
`0.10`，得到 12 个 shot，时长依次为
`5.100, 1.433, 0.600, 0.667, 0.700, 0.567, 3.933, 1.067, 3.966, 1.234, 1.300, 1.366s`，
确定性先验判为 `proof_montage`。

### 实现与本地验证

新增 `EvidenceUnit`、参考编辑模式抽取、细粒度 Evidence Miner、Evidence Planner、
Micro Montage Renderer、完整 V6 pipeline 和 4×2 GPU 常驻进程池。40 秒连续镜头按
`max_watch_s=6.0`、`overlap_s=0.5` 被确定性拆为 8 个真实 Omni 调用；每次保存输入
区间、raw response、采样记录和实际 GPU pair。

本地合成媒体集成测试真实执行 FFmpeg，完成：

```text
CLI/spec → scoped shots → split mining → evidence plan
→ content_master.mp4 → source_only / bgm_mix
→ decoded-frame checksum → blind review → human pending
```

第一次集成测试发现两个实现错误：

1. 把 V6 的 `max_unit_duration_s=2` 硬编码进通用时间解析后，
   `[20,30] relative + origin=2965` 的坐标审计用例被误删。修正为通用解析只负责坐标，
   2 秒上限由 Evidence Mining 策略显式传入。
2. BGM 分支使用 `-t 4.5`，而 source_only 直接复制母版；即使 `-c:v copy`，两者的
   帧数/时间边界仍可能不同，decoded frame checksum 失败。移除音频派生阶段的二次
   截断后，两个版本按母版自然结束，逐帧 checksum 一致。

本地最终结果：

| 检查 | 结果 |
|---|---|
| 全量 pytest | **458 passed in 20.49s** |
| V6 定向测试 | **12 passed** |
| Ruff（新增/修改文件） | PASS |
| Python 3.10 AST | 10 个文件 PASS |
| 合成媒体双版画面 | decoded-frame checksum 完全一致 |
| 人工门控 | 自动通过时仍不生成根目录 `rendered.mp4` |

## 诊断依据

1. 参考视频用默认 `threshold=0.30` 只有 1 个 shot，而 `0.10` 有 12 个，说明“参考
   编辑结构缺失”首先是切点灵敏度问题，不是视频本身没有剪辑。
2. w15 即使源片 shot detector 只产生一个 40 秒容器，固定 6 秒 tile 仍会形成 8 次
   Omni 观察；这把“源片是长镜头”和“模型只能做一次粗理解”解耦。
3. 时间归一化单测证明 10 秒 raw interval 本身可以是合法坐标；只有进入 V6 Evidence
   策略后才因时长上限被拒绝。由此排除“解析器应该同时决定编辑粒度”的设计。
4. 合成媒体第一次 frame checksum 失败时，视频编码明确为 copy；移除 `-t` 后通过，
   坐实差异来自派生时长边界，而不是 BGM 改变了像素。
5. Qwen3-Omni thinker 既有真机记录约需 69GB；单卡方案在容量上不成立。服务器预检
   显示 8 张 A6000 各约 49GB 且启动前均空闲，因此 4 个两卡实例是能实际并行的最大
   配置，而非仅在配置文件里写“8 卡”。

## 选择与理由

选择独立的 Evidence 表示层：Perception 只决定“事实在哪一帧/哪一秒”，Editor 只做
选择和按原片时间排序，不能改写 Evidence 区间。普通微片段严格限制为 0.15–2 秒，
关键帧可渲成 0.3–1.5 秒 hold；计划至少包含 Hook 和另外两种证据功能，且不为接近
preferred duration 添加无功能素材。

参考视频既保留确定性 cut statistics，也让 Omni 只学习编辑语法，不把参考人物或剧情
迁移给电影。最终成片由同一 Content Master 派生两种音频；blind reviewer 看真实 mp4，
不接收 Evidence Plan。所有自动条件通过后仍保持 `delivery=blocked`，直到人工确认核心
表达、Hook、连贯性和两个音频版本。

并发采用持久 4-worker 进程池。每个 worker 在 import torch 前设置自己的
`CUDA_VISIBLE_DEVICES`，模型加载一次后连续处理多个 tile；Evidence Mining 的 8 个
请求可四路分发，最终两版 blind review 也可并发复用已加载实例。

## 从结果学到什么

1. 镜头容器与感知调用粒度必须分离；真实长镜头不能强迫模型只做一次长段总结。
2. 通用时间解析只负责坐标正确性，编辑粒度上限必须由具体实验策略控制。
3. “视频流 copy”不自动等于逐帧集合一致；派生分支的 `-t` 也会改变帧边界，必须用
   解码后逐帧 checksum 验证。
4. 充分使用 8 卡应按模型实际显存拆成可容纳的并发副本；对本模型是 4×2，而不是
   8×1，也不是在一个实例上盲目扩到 8 卡。
5. 自动 pipeline 完成与正式交付是两种状态；后台跑通也不能跳过独立 blind review 和
   人工 acceptance。
