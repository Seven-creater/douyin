# 2026-09-13 72 窗夜链与八卡分片并行实录（工程线）

> 时间跨度 09-12 20:16 → 09-13 00:01。从"3 窗门控五判据全过"放行到 72 窗
> pack-on 全量重标收工。本文只记**工程**（并行/防断/进程坑谱系）；内容结论
> 见姊妹篇《V4_C2C3_身份体系打通与localize抽象需求死局》。

## 背景与问题

72 窗（film1 36 + film2 36）pack-on 重标是解锁 V4 身份饥饿的唯一路径（V4_C
实证）。单实例串行估算 5h+；用户要求"能并行就并行、每阶段可续、绝不白跑"。
共享服务器 + 裸 transformers 部署决定了并发=多进程多实例（每 Omni 实例 2 卡）。

## 候选方案

| 方案 | 思路 | 预期优劣 |
|---|---|---|
| A 串行单实例 | 历史默认 | 稳但 5h+，且中途挂=全重来（无外层守护） |
| B 双片并行 | film1/film2 各一实例（不同输出文件，零代码） | 2× 提速，实现零风险 |
| C 同片分片并行 | 窗口分片×独立输出+合并（需新基建） | 4× 提速到八卡满载，但要动输出路径与合并 |
| D 前台 ssh 长链 | 一条 ssh 串全部阶段 | 最简单，已实锤会断（55min 连接掉线） |

## 实测/对比

- **D 先踩**：pack 重建+门控串一条 ssh → 重建成功后连接被服务器掐断，门控
  没跑（exit 255）。教训固化：长任务必须 setsid 脱离，ssh 只负责发射。
- **B 落地**（night_72b）：film1 断点续跑（11/36 成果保留）∥ film2 全量，
  2×2 卡。随即被用户指出八卡全空（卡 3 的他人 vllm 已退）——升级 C。
- **C 落地**（night_72c/72c2）：
  - 基建入库（3516cf3）：`run_narrative_annotations(output_path=)` 分片
    独立输出 + `merge_annotation_shards` 并集合并（冲突窗跳过+报告）+ 单测。
  - 部署：film1 剩余 22 窗→2 分片（卡 0,1/2,3），film2 36 窗→2 分片（卡
    4,5/6,7），21:23 八卡满载（每卡 41-45GB）。
  - **实际耗时**：film1 两分片 ~45min（11 窗×4min/窗）；film2 ~85min +
    补漏 11min。实测 ~4min/窗（prompt v3 多实体纪律让生成变长，高于此前
    1min/窗的估计）。

## 诊断依据（五类进程坑谱系，每一类都有实锤）

| # | 坑 | 实锤现场 | 修复 |
|---|---|---|---|
| 1 | **pgrep 自匹配→收养活锁** | 编排器"收养"循环等一个永不退出的"分片"——真身是启动它的 ssh wrapper 残留 bash（cmdline 含 `job_shard.py` 字样）；看门狗对此盲区（编排器活着但空转） | 收养/看门狗 pgrep 全部锚定完整路径 `^/data02/...python /tmp/xxx.py`；杀精确 PID 解锁 |
| 2 | **CRLF** | watchdog 脚本 Windows 写出带 `\r`，bash 语法错**静默秒死**——"有看门狗"是错觉（链稳是运气） | 上传后 `sed -i 's/\r$//'` + `bash -n` 先验 |
| 3 | **flock 孤儿继承** | 换看门狗时旧实例的 `sleep` 子进程继承锁 FD 不放，新实例 `flock -n` 永远失败 | 杀孤儿持有者；锁文件属一次性守护场景 |
| 4 | **无界重试烧夜卡** | V4 若反复失败，看门狗每 ~50min 重拉一轮直到天亮 | watchdog v2：最多 3 次，超限写 `gave_up` 标记退出 |
| 5 | **多任务串一个前台 ssh** | 见方案 D；另两次 ssh 组合命令 exit 255 | 一任务一发射；本地任务设短超时+杀本地不等远端 |

防白跑四层（最终形态）：逐窗原子落盘+completed 三处扣除（主文件/分片）→
分片 rc 门禁 → 收养+补漏编排（flock 单实例）→ 有界看门狗+阶段标记
（`72c_markers/annotations_done|merge_done|video_done`）。

## 选择与理由

选 C（在 B 之上演进）。关键取舍：**同片分片会让跨窗 vis_ id 空间分裂**——
可接受，因为 V4 身份键本来就是窗口作用域+bindings 承载跨窗（这正是门控验
证过的设计）；registry 累积提示每分片独立起点，轻微损失召回换 2× 提速。

## 验证

- film1 completed 36/36、film2 33/36（3 窗两轮 parse 失败降级——raw 答案
  未存，待查模式）。
- merge 两片零 conflicts；索引重建 1124 行；`update_pack_from_annotations`
  回填 auto registry：wuxian 44 窗 / xiaohei 10 / fengxi 8。
- `video_done` 标记 00:01 落盘，V4_C2 成片产出（内容结论见姊妹篇）。
- 未测路径：编排器中途被 OOM killer 杀死的真实重拉（watchdog 逻辑有单次
  人工触发验证：杀旧编排器→新实例收养→补漏→收尾，全程如期）。

## 从结果学到什么

1. **"有守护"必须验证守护本身活着**（CRLF 静默死教训）——监控的监控。
2. 共享服务器上 **cmdline 字符串就是全局命名空间**：模式匹配一律锚定完整
   路径；setsid 的孤儿会继承锁与管道，清理要按会话组。
3. 用户拍板"并行到顶"是对的，但要配套** rc 门禁+幂等合并**，否则提速放大
   的是脏数据产出速度。
4. 估时按"单窗实测"重算（4min/窗），别按历史均值（1min/窗）——prompt v3
   的多实体纪律改变了成本结构。
