# 2026-09-16 P0：V9 参考理解可靠性修复

## 背景与问题

V9-G 依赖 V9 的三个 Program，但旧 V9 路径允许未标源片 SHA／工具版本的 OCR、ASR、节拍缓存进入证据；Edit Program 主要根据全局理解文本推导，没有逐 Section 回看原片。这样即使 JSON 能解析，也不能证明“每刀新增什么信息”。本轮用户拍板仅修 P0，不进入 Unit、H3 或渲染。

## 候选方案

| 方案 | 思路 | 预期优劣 |
|---|---|---|
| A | 继续读取旧缓存、靠全局观看与切点推 Edit | 成本低，但来源不可审计，切点数量会被误当作 montage 证据 |
| B | 旧缓存无证明即不可用；Global 初看后逐 Section 直接看原视频，按解释缺口 Probe | 多次观看有成本，但每层有原始响应、输入哈希和可定位的失败原因 |
| C | 直接扩大生成／Repair 轮数弥补参考理解 | 未测；参考含义若错，下游生成不能纠正上游真值 |

## 实测/对比

- 本地参考片 `data/videos/7682719919410072847/video.mp4`：FFprobe 显示 21.933333 秒、30fps、658 帧；新确定性证据读取了 658 帧 PTS，合并得到 18 个候选切点。这是**候选**，不是已确认的 18 刀。
- 现有 `ocr.json`、`transcribe.json`、`beats.json` 均未携带本轮要求的源片 SHA 与工具源码版本：三项状态均为 `unverified_source`，新证据账本不复用其内容。
- P0 专项回归 43 项通过；仓库全量回归 633 项通过；Ruff 和 Python 3.10 语法特性检查通过。这些是工程合同检查，不代表 Omni 已理解参考片。
- 服务器 GPU 0–7 查询时均为 100% 利用率、每卡约 21.2 GiB 已用。遵循用户先前“别人正在用就停”的要求，没有启动 Omni，也没有中断其他任务。
- 真实三 Program、逐 Section 人工签署和冻结 SHA：**未测，原因是共享 GPU 正在被占用；本阶段结果仍为 BLOCKED，不进入 P1。**

## 诊断依据

先核对参考源片与旧证据缓存，发现“缓存存在”不等于“与当前源片和工具版本匹配”；因此没有把旧文字与节拍结果当成可靠证据。随后将 Global Watch 限定为粗 Section 提议，每个 Section 的 Edit 解释必须来自原片复看、候选切点及该范围可用的 OCR/ASR/音频信号。对于未解释的密集切点、未引用的文字／语音等才生成 Gap；孤立已解释信号不触发额外观看。当前还没有真机 Omni 输出，故不能从测试通过推断模型的画面理解能力已经改善。

## 选择与理由

选择方案 B。可信度优先于无来源缓存的覆盖率；Section 复看优先于“看到切点就猜剪法”。连续性采用 `required / preferred / not_required / unknown` 四态，避免把未知静默当作不需要。旧 V9-G 对 P0 新 schema 显式拒绝，避免在未适配的布尔接口里误读。

## 验证

- 已验证：旧缓存拒绝、无剧透生产 Prompt、Section 原视频调用、切点解释缺口、OCR Probe 携文字事件和对应源帧、`unknown` 冻结阻断、人工修订需再次做迁移性审核、旧 V9-G 版本阻断；全量测试通过。
- 待验证：真实 Omni 逐段解释是否与原片一致、Probe 是否真实解决 required Gap、三个 Program 是否通过人工逐段观看和匿名 Requirement Transfer Test。
- 残留风险：本次 OCR/ASR/节拍作为不可用而非重算，实际参考理解可能缺少文字和节奏证据；只有真机运行和人工看原片才能判定。不可用不得被解释为“片中没有”。

## 结果

代码侧 P0-A/B/C/D 和自动门控已实现；真实 P0 交付仍 **BLOCKED**。没有签署或冻结三个 Program 的 SHA，没有启动 P1、H3、生成或渲染。真实运行应在 GPU 空闲且 OCR/ASR/节拍来源可证明时进入独立 run 目录，再执行人工验收。

## 从结果学到什么

缓存必须沿“源视频 SHA＋工具版本＋上游输入哈希”失效；切点只能提出调查问题，不能证明编辑结构；工程测试通过只说明门控按设计工作，不能代替模型真机理解与人工逐段验收。
