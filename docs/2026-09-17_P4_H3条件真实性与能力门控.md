# P4：H3 条件真实性与能力门控（CPU 阶段）

> 代码提交：`858fb16`。本记录只报告已执行的 CPU/假后端检查；未运行真实 H3、Omni 或 GPU 条件有效性实验。

## 背景与问题

旧能力探测把生成的 MP4 文件存在且非空当作某种 H3 条件“可用”。这只能证明接口返回媒体，不能证明参考图、参考视频、音频或首尾帧真的进入请求并影响输出。P2 的条件预览此前也没有把资产字节、语义角色、请求标签、顺序和正式生成入口闭合为一条可复核的链。因而即使条件被遗漏或错位，后续仍可能把产物当成正式生成结果。

## 候选方案

| 方案 | 思路 | 取舍 |
|---|---|---|
| A：沿用 MP4 成功即能力通过 | 最少改动 | 无法区分 transport 与 conditioning；拒绝。 |
| B：仅在 CLI 生成前检查条件 | 入口简单 | 直接调用 Python API 仍可绕过；拒绝。 |
| C：资产—Prompt—Request—能力证据分层校验，并在 CLI、执行函数和正式验收复核 | 可追溯且 fail-closed | 需要更多清单与测试；本轮选择。 |
| D：立刻启动真实 H3 做全部能力冒烟 | 可获得真正有效性证据 | 本轮明确不使用 GPU，且 P0 尚无真实人工冻结；未测。 |

## 实测/对比

- P4 计划生成 S0–S7 八种冒烟用例；无 fixture 时全部保持 `planned_only`，能力注册表全部为 `unverified`。
- 使用 FFmpeg 合成图片、4 秒 H.264/AAC 视频和 WAV 后，八个请求的素材、标签、顺序、SHA 与媒体类型均通过完整性检查。`--phase capability --plan-only --fixture-dir ...` 能输出每例 `request.json`、`condition_manifest.json` 与 `assets.json`，不会启动 H3。
- 假后端对照：honest、丢弃视频条件、重排图片条件都能返回可解码 MP4；后两者的条件效果检查失败。假后端的 honest 结果仅标 `fake_only`，不提升真实能力注册表。
- 故障注入覆盖缺失 `<Video 1>` 对应条件、未在 Prompt 声明的图片、图片顺序交换、素材 SHA 不符、参考人物身份角色违规、未接受的 memory 尾帧，以及仅伪造内存授权对象。上述路径均阻断。
- 定向测试 45 项通过；全仓 `pytest -q` 为 **671 passed**；修改文件 Ruff、Python 3.10 AST/import 和 `git diff --check` 通过。
- 真实 H3 的条件影响、不同 variant 的服务能力、真实 Omni 观察与人工验收：**未测**，原因是本轮限定 CPU/假后端且真实 P0 Program 尚未人工冻结。

## 诊断依据

假后端“丢视频”与“换图顺序”仍可产生合格 MP4，却不能保留声明的条件语义，直接排除了“媒体传输成功即可证明条件有效”这一假设。仅在 CLI 检查仍存在执行函数直调路径；加入磁盘冻结快照、请求哈希、资产清单和注册表的执行前复核后，伪造 `formal_authorization={passed: true}` 的测试在任何 H3 网络请求前被拒绝。正式验收再次检查产物不是 `simulation_only`，防止 CPU 假结果被误称为正式视频。

## 选择与理由

选择 C，并将能力状态显式区分为 `unverified / transport_only / effective / unsupported / failed`。P4 使用项目自有的请求/条件清单；H3 请求标签按图、视频、音频各自编号，hybrid 先保留参考条件再附首尾关键帧。这与 [SGLang H3 cookbook](https://github.com/sgl-project/sglang/blob/main/docs/cookbook/diffusion/MiniMax/MiniMax-H3.mdx) 的请求结构相符，但文档支持不等于本机实际有效。生产入口要求真实能力证据，不让假后端或旧 MP4 探测结果升级为 `effective`。由于修复控制器尚未纳入条件重校验，真实入口暂把 repair 次数设为零，避免第二次生成发出未经核对的新请求。

## 验证

本阶段“已解决”的判据仅限：CPU 路径能识别条件遗漏、顺序或字节漂移；未验证能力不能启动正式 H3；假结果不能形成正式 `rendered.mp4`。这些判据已由上述测试覆盖。尚不能判定真实 H3 的任何条件有效性，也不能宣称 P4 正式生成链路已放行。下一步必须在 P0 人工冻结且资源可用时，逐项保存真实请求、响应、媒体、条件效果和人工复核，再单独把相应能力提升为 `effective`。当前 CLI 的非 `--plan-only` capability 执行有意阻断。

## 结果

P4 的 CPU 规划、条件真实性门控与假后端故障注入已完成并提交。正式 H3 生成仍为 **BLOCKED**：没有真实能力注册表与人工冻结的 P0 Program；本轮没有调用 GPU/Omni，没有新成片。

## 从结果学到什么

“接口成功、文件有效、条件生效、内容合格”是四个独立断言，不能用前者代替后者。对每次生成保留资产 SHA、请求标签/顺序和冻结 Program 依赖，可让条件丢失在 H3 调用前阻断；对未知的能力保持 `unverified`，比自动推断支持更可靠。真实条件效果仍需要可观察的对照和人工确认，不能由假后端测试外推。
