# 2026-09-13 V5.1 w15：从智能片段提取到真实编辑决策

## 背景与问题

V5 w15 已经能在 `luoxiaohei1 / 2965–3005s` 内定位、核验并完整保留“人和妖
不能简单按类别判断好坏”的核心内容，双音频也能从同一个 Content Master 派生。
但 v6 的 `content_master_render/work/concat.txt` 只有一个 `segment_0001.mp4`，实际
执行是把 `2976.62–2998.62s` 连续截取 22 秒。它证明了 retrieval + trimming，
没有证明 Agent 会决定“为什么切、删什么、下一段承担什么功能、为什么结束”。

用户据此拍板 V5.1 仍固定同一 40 秒 scope，不回 72 窗、不启用 Gap Watch 或
Film Bootstrap，只在 Evidence Verification 与正式 Render 之间增加独立 Editorial
Planning。实验目标不是保证得到一条好视频，而是定义并验证
`editorial_transform_present`：内容可能成立，但没有真实编辑变换时必须以
`editorial / extraction_only` 阻断，不能冒充剪辑成功。

## 候选方案

| 决策点 | 方案 A | 方案 B | 选择 |
|---|---|---|---|
| A/B/C 选择依据 | 只看 Edit Plan JSON 后选 Top1 | 每个合法方案先做低成本真实 preview，再零上下文盲评 | B；JSON 看不见切半句、跳姿势和音频断裂 |
| 候选下限 | 必须至少 3 个 | 最少 2 个、目标 3–5、最多 5 | B；避免为了数量加入空镜 |
| “有 cut”的语义 | 直接等同编辑质量 | 单独记 `editorial_transform_present` | B；有 cut 不等于好 editing |
| cut reason | 任意自然语言 | 固定 enum + 人读 detail | B；防止“为了节奏”等套话通过字符串检查 |
| candidate function | 候选自身标成 question/core/ending | Observation 只记事实，Planner 提议 function，preview verifier 验货 | B；避免 Planner 循环自证 |
| 分数门槛 | hard boolean + 总分至少 75 | hard boolean 决定 eligible，分数只排序 | B；75 没有经验分布依据 |
| 音画关系 | 首轮支持 J/L cut | 音画锁定、只删不重排 | 后者；降低因果伪造与对白错位变量 |

三种固定编辑假设保留：`viewpoint`、`question_answer`、`core_close`。任一假设
缺少真实素材时允许 `unsupported`，不把普通陈述硬解释成问题或结尾。

### 本地实现结果

新增 `edit_plan_v1` 编辑层：

- 从完整 ASR utterance、已核验 required evidence 和镜头边界建立 2–5 个候选；
- 候选观察调用只记录实际对白、动作和局部人物外观，不写编辑 function；
- Planner 只能引用 candidate ID，时间区间由程序回填且不可改；
- 固定生成 A/B/C，确定性检查后为每个合法方案渲染 640px、12fps、低码率真实 preview；
- Blind Editorial Review 只看 preview mp4，不接收 Story/Edit Plan；
- 四个 hard boolean 决定 eligibility，五项分数只在合法方案之间排序；
- Top1 被映射为 renderer 的多个真实 segment，之后才生成唯一正式 Content Master。

新增合成媒体端到端测试真实调用 FFmpeg 生成 40 秒带音轨视频和 BGM，fake runner


### 服务器 v1：阻断结果与新证据

`ce58823` 在 GPU 0/1 上完成首轮真实执行。Evidence 定位为
`2978.12–2981.12s`，之后 verify 和 deterministic story check 通过；编辑门控则
正确阻断：

```text
failure_class: editorial
editorial previews: 0
delivery: blocked
root rendered.mp4: absent
```

该轮暴露了两个可复现问题。第一，ingestion `result.json` 中进入 scope 的
`shots` 实际是 `2965–2985s` 和 `2970–3005s` 的粗窗口容器，不是局部镜头边界。
第二，Planner 原样复制了 prompt 中以 `|` 连接的 enum 示意文本，
确定性检查因 `invalid_function / invalid_cut_* / required_evidence_not_covered`
拒绝了它。这是真实阻断，不是内容失败或渲染失败。

针对这两个问题，`90ff7e8` 不再把 ingestion 粗窗口交给 Editorial
Planner，而是只在批准的 40 秒 scope 内运行 FFmpeg scene detector，并用
`setpts=PTS-STARTPTS + timebase_origin_s` 把切点审计地归一为源片绝对时间。
Planner prompt 也改为单值 enum 示例，并明确要求每个 supported 方案覆盖
required evidence。

### 服务器 v2：粗窗口隔离后的实际结论

`90ff7e8` 的 v2 成功使用了 scope-local detector，但它仍把一个 40s
无切长镜和 scope 边界 ASR 残片交给候选层。结果为：


Planner 只提出了 `viewpoint` 的 3 段方案，但总时长 `38.84s` 超过上限；
`question_answer` 和 `core_close` 因缺少真实问句/收束反应而 unsupported。

## 诊断依据

1. v6 的语义盲审和双音频都通过，但 concat 只有一个 segment，排除了“仍然不会找
   内容”这一旧诊断，坐实问题位于 Evidence 之后、Render 之前。
2. 当前 renderer 已按任意 slot 数量切段并 concat，多段合成测试也成功，排除了“必须
   重写渲染底座”。新增层只需生成正确的 asset/retrieval adapter。
3. Edit Plan 文本无法暴露半句截断和姿势跳变，因此 Planner 自评不能作为 Top1 依据；
   只有让 Omni 盲看真实 preview 才能区分“JSON 合理”和“剪出来合理”。
4. `candidate_min=3` 会把候选数量变成隐性填充目标，和此前强凑 22 秒属于同类错误；
   下限改 2 后，真实的 question→answer 两段结构仍可参加实验。
5. 固定 reason enum 让程序验证结构，`reason_detail` 只服务人工审计；相比检查任意非空
   字符串，它能阻止套话伪造确定性证据。
6. 实际 ingestion 产物名为 `shots` 不代表其粒度真的是镜头；v1 候选的 20/35
   秒区间与窗口完全对齐，证明编辑层需要自己的 scope-local shot geometry。

## 选择与理由

最终实现 `roughcut_v3`，V2 仍能读取历史数据，但不能正式交付。生产链保持
chronological + A/V locked；Edit Planner 只能 selection/omission，不拥有 Evidence
时间。required dialogue 使用完整候选区间，若同一 required utterance 的多个片段之间
出现 source gap，确定性检查报 `required_dialogue_internal_gap`。

`editorial_transform_present` 定义为：至少两个 segment，且相邻已选源片之间至少有
一次 `≥0.25s` 的真实省略。它仅证明发生了 editorial compression，不声称剪辑质量；
质量由真实 preview 的四个硬布尔验证。若内容清楚但没有真实省略，保留 preview 和
审查证据，按 `failure_class=editorial / reason=extraction_only` 阻断。

cut reason taxonomy：

```text
cut_in:
question_starts | speaker_change | new_information |
core_statement_starts | reaction_starts | visual_subject_change

cut_out:
question_complete | semantic_unit_complete | answer_complete |
reaction_complete | redundant_content_starts | next_function_begins
```

最终 source_only / bgm_mix 仍从同一个正式 Content Master 派生；preview 不会替代
最终双版本 blind review 和人工 acceptance。

镜头候选的时间几何也固定为编辑层自己的 scoped detector 产物：FFmpeg
只 seek/decode `source_scope`，`showinfo` 输出强制为相对时间，再对每个端点加同一个
`timebase_origin_s`。它不会扫全片，也不会自动扩大 scope。

## 结果

本地工程链已经完成，v1/v2/v3 均按门控设计阻断，没有任何根目录正式
`rendered.mp4`。本轮 V5.1 结论为 **BLOCKED：该 40s scope 可证实内容完整，但未证明存在
可实施的 editorial compression**。

## 从结果学到什么

1. 计划正确不等于成片正确；涉及剪辑连续性的选择必须后移到真实 preview 之后。
2. 数量目标和时长目标都会诱导填充，应该设 target 而不是把 target 变成内容硬门槛。
3. “发生变换”和“变换有价值”必须用两个字段表达，否则一个机械 cut 就会冒充能力提升。
4. LLM 适合提出编辑解释，不适合给自己的解释提供事实依据；Observation、Proposal、
   Verification 必须分层。
5. 第一版剪辑应只删不重排、音画锁定；先证明 communicative compression，再增加高级
   时序手法。
