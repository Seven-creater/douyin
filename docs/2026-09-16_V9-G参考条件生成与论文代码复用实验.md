# V9-G 参考条件生成与论文代码复用实验

## 背景与问题

V9 已把参考视频拆成 Content Program、Edit Program 和 Material Requirements，但项目还缺少一条受约束的生成链：如何把已冻结的参考程序编译成 H3 可执行任务，如何在生成后重新观察而不是相信生成器，以及如何避免第三方论文代码反过来定义本项目的研究表示。

用户拍板的主线是：

```text
V9 Reference Programs
→ first-party Generation Contract
→ FilmDSL execution adapter
→ H3
→ Generate–Observe–Repair
→ Evidence Moment Selection
→ Micro-edit
```

本轮还必须满足三个现实约束：

1. 复用论文开源代码前必须阅读实际仓库和许可证，不能按论文印象虚构 API；
2. `generation_contract.json` 必须是唯一业务真值，FilmDSL/H3 只能派生，不能反写；
3. 服务器 GPU 正被其他任务使用时不得抢占、杀进程或把资源冲突伪装成模型失败。

## 候选方案

| 方案 | 思路 | 预期优劣 |
|---|---|---|
| A：直接采用 CineCrew/NEWTON 内部类 | V9 Section 映射到上游内部 schema，直接调用其 loop | 开发快，但被未承诺稳定的内部类名绑死；研究贡献边界模糊 |
| B：复制整套上游 pipeline | 把规划、资产、重试、审片全部搬入项目 | 功能多，但可能把本项目退化成胶水集成；依赖和许可证面扩大 |
| C：固定 commit，只复用非贡献性基础设施 | first-party Contract 与决策逻辑；上游只通过 JSON/dict adapter 提供 trace/memory | 边界清楚、可审计，需多写一层稳定适配 |
| D：自行重写所有基础设施 | 不引入第三方代码 | 控制最大，但违反本轮“先读论文代码并复用”的要求，也重复造轮子 |

H3 条件路由另有两个候选：

| 方案 | 思路 | 取舍 |
|---|---|---|
| 禁止 Ref2VA 与首尾帧混用 | 一律拆 Unit | 与当前 SGLang 官方能力不符，会无谓损失联合约束 |
| 先做 capability smoke，再启用 hybrid | reference 与 `frame_index=0/-1` 同时保留；不支持才显式拆分 | 符合官方请求协议，但不能按文档预填成功 |

## 诊断依据

本轮最关键的判断不是“能不能发一个 H3 请求”，而是哪些层能被证实、哪些不能。

1. SGLang 官方 cookbook 明确给出 `frame_index=0/-1` 和 Ref2VA hybrid 规则，排除了“reference 与首尾帧架构上绝对互斥”的旧假设。
2. CineCrew/NEWTON 仓库中确实存在内部 schema/memory 类型，但它们不是稳定跨项目 API；固定源码 SHA 加序列化 adapter 比直接 import 上游内部类更可控。
3. 合成媒体全链路证明状态提交时机、三层审查和正式文件门能工作；它只证明工程控制流，不证明 H3 画面质量。
4. 服务器 GPU 进程表证明当前不能做干净 capability smoke；若强跑，OOM/变慢无法归因到 V9-G。
5. 缺少 V9 frozen hashes 与许可证签署是更早的政策门。即使 GPU 空闲，也不能跳过这两个门直接生成。

## 选择与理由

选择方案 C：

- `generation_contract.json` 保持 first-party canonical；
- FilmDSL 是包含 `meta/assets/memory/clips[]` 的派生执行字典；
- CineCrew 只提供改造后的 artifact trace；
- NEWTON 只提供 bounded loop memory/trace，并由 `NewtonTraceAdapter` 隔离内部类；
- H3 请求严格使用官方 root model path、variant 和 conditions 协议；
- 中性观察与合同核验是同一 Omni 的 prompt 隔离两阶段，不包装成两个独立模型；
- rejected attempt 永不修改 memory，只有 Raw Unit 与 Snippet 都通过且 transition 合法才 append state commit；
- 正式 `rendered.mp4` 必须等 Section、最终盲审和人工验收全通过。

该方案牺牲了“马上调用所有上游能力”的速度，换来研究贡献边界、缓存依赖、许可证、失败归因和状态污染防护的可审计性。

## 结果

代码、CLI、许可证门、上游锁、H3 路由、渐进修复、Moment Selection、状态提交、三层验收、指标和部署脚本均已落地，并推送/部署到提交 `4278d37`。

真实 V9-G 实验结果为：

```text
BLOCKED before capability/generation
```

阻断原因按顺序是：`V9 frozen programs missing`、`license gates not passed`、`GPU resources occupied`。这不是“待回填”，而是本次运行环境下的真实门控结果；系统没有生成 capability 假证据，也没有产生正式视频。

## 从结果学到什么

1. “论文写了支持”只能生成测试项，不能直接生成 capability `true`；真实请求、响应和媒体哈希才是能力证据。
2. 上游代码应固定源码和许可证，同时把不稳定内部类挡在 adapter 后面；研究表示不能依赖第三方类名。
3. Raw 生成成功不能给裁剪和 Section 背书；每次信息压缩都会引入新的语义风险，必须重新验收。
4. 状态记忆必须是接受后的 append-only commit，而不是把最近一次生成结果直接当事实。
5. 资源占用、许可证和输入冻结属于实验前硬门。把这些失败与模型内容失败分开，才能保证后续 H3/Omni 结果可归因。
6. 两 Unit 只能证明工程链路；正式机制结论必须达到至少 4 条参考、每条 6 个 paired units，并对 D/E 同时匹配请求数、生成秒数、GPU 时间和推理配置。
