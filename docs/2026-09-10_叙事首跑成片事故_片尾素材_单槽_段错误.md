# 2026-09-10 叙事库首跑成片事故：片尾素材 / 单槽零剪辑 / cv2 段错误

三起串联事故，同一目标（叙事库 e2e 出可看片子）下的素材、规划、基础设施各爆一处。
全部有实证定位，修复后 321 单测全绿。

## 事故 1：成片 = 片尾 ED 职员表（用户亲自看出）

**现象**：full_narr_v3 的 60s 成片，开头帧是日文制作名单滚动（"小学館/exsa/PV編集…"），
中段帧是产屋敷耀哉特写但右侧叠满 OP/ED 职员表（"音楽：椎名豪、梶浦由記"），全程无中文字幕。
用户原话："一点都没剪辑啊，这就是片尾还是片头，右边全是字幕，这种片头片尾就该删掉"。

**定位**（服务器实测）：
- 电影总长 9295.8s；选中素材 w034 = 9060-9105s = **片尾最后 3.5 分钟**。
  w033（少年城市上空飞行）/w034（城市夜景）/w035（日落挣扎）全是 ED 段画面。
- 选窗（select_narrative_windows）与检索都没有"片头片尾"概念，ED 窗口正常进标注、进检索池。

**修复**：新增 `src/agentic_video/zones.py` 集中排除规则——长片（≥30min）片头 90s +
片尾 360s 不进检索池；时长优先取 sources/*/*.json 扫描信封，兜底用行内最大 end_s；
预告片/短切片不受影响。三处接入：narrative_index 选窗、story_planner 叙事检索、
planner 编辑检索（rank_asset_slots 增加 excluded_rows）。config `library.source_zones` 可调。

## 事故 2：60 秒单槽零剪辑

**现象**：story_plan 只有 1 个槽（hook [0,60]），素材从头到尾一个窗口连放。

**定位**：参考片（7668… 抖音爆款 25.3s）的 Narrative Program 是旧代码生成的缓存——
arc=[hook]、2 事件、uncertain、init=1 窗（现行代码应为 3 窗）。story_planner 按弧段开槽，
弧薄则槽少，无兜底。

**修复**：
- `_expand_thin_arc`：arc<3 段时按冲突→高潮→结局补位，事件引用按时序切块（早期冲突/
  后期高潮），补位段带 synthesized 标记；两入口（build_story_plan / build_story_plan_from_index）
  统一接入，计划记录 arc_expanded 供溯源。多槽经兼容角色池自然分流素材。
- 服务器侧废弃旧缓存（result.json.bak_thin_arc_20260910），重跑用现行 narrative_agent
  （含精化循环）重新归纳参考片叙事程序。

## 事故 3：e2e 三连段错误（基础设施）

**现象**：full_narr_v4 启动后约 1 秒（走完缓存阶段、进入 Omni 模型加载）SIGSEGV
core dumped，无 Python 栈；重试三次同位置必崩。期间还伴随 /data02 瞬时抖动（ssh 连接
重置、日志文件"看不见"的幻象）与 dmesg 里 libarrow/jemalloc 线程崩溃（后证实是 GPU4/5
上别人的进程，红鲱鱼）。

**定位**（二分复现，各 2/2 稳定）：
- `import cv2` → Omni 四卡加载：**崩**
- `import src.library.signals`（引 cv2）→ 加载：**崩**
- `import torch` → `cv2` → 加载：**过**
- 纯加载（无 cv2）：**过**；`import src.perception.transcribe_audio`（不引 cv2）→ 加载：**过**

根因：cv2 与 torch 的原生 OpenMP 运行时冲突，cv2 先进进程时 Qwen3-Omni 多卡加载必崩。
仓库 signals 等模块 import cv2，而 cli 的 handler 延迟导入 pipeline（→cv2）后又同进程
加载 VLM——次序正好是致命的 cv2→torch。此前 full_narr_v3 能跑通属于侥幸（冲突对内存
布局敏感，非确定性）；narrative 标注任务进程不引 cv2，故从未触发。

**修复**：`cli.main()` 在进入任何 handler 前 `_preload_torch_before_cv2()`（本地无 torch
静默跳过），保留 set_visible_gpus 先于 torch 的次序。回归测试用子进程实测
`import src.agentic_video.cli` 不得拉起 cv2（否则预载失去排序控制权）。

**教训**：
1. "无栈的段错误"先想原生库冲突，用**最小导入组合二分**（本次 15 分钟定位）；
   dmesg 里的崩溃行要先核对 pid 归属再当证据。
2. 侥幸通过 ≠ 无病：v3 能跑掩盖了.cv2→torch 的致命次序，事故只是时间问题。
3. 监控命令里 pgrep -f 的模式会匹配自己的 bash 包装进程（本次两次假阳性"RUNNING"），
   判活要用 GPU 显存/产物文件这类旁证。
