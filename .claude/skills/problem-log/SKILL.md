# 工程问题与决策记录

每次解决一个**非平凡**问题或做出**带取舍**的决策，必须写一条记录到 `docs/`。

## 何时触发（自动，不必用户提醒）

1. **bug 修复后**：排查链 ≥2 步、或造成了实际损失（GPU 白跑/返工/数据丢失）的 bug；
2. **技术选型后**：存在 ≥2 个真实候选方案（含被否决的），无论谁拍板；
3. **实验/对比完成后**：多方案实测有了数据（含失败数据）；
4. **阶段收尾时**：结果栏为"待回填"的旧记录此时必须补齐；
5. **结果审查/验收时**：判断"问题到底是怎么样的"和"问题有没有真解决"的过程本身——
   必须记录**区分假设的关键证据**（哪条数据把假设 A 排除、把假设 B 坐实）和
   **解决判定标准**（用什么复现/产物数/指标/人工检查确认修好），以及**未验证的残留风险**
   （哪些路径没测到、判定强度够不够——"代码改了"不等于"问题解决了"）。

## 怎么写

1. 从 [docs/_模板.md](_模板.md) 复制，命名 `docs/YYYY-MM-DD_主题.md`；
2. 六段缺一不可：背景与问题 / 候选方案 / 实测对比 / 选择与理由 / 结果 / 从结果学到什么；
3. 规矩（见 docs/README.md）：实测数据照抄（失败也是数据）；没测的标"未测+原因"；
   用户拍板的注明"用户拍板"；结果可"待回填"但阶段结束必须回填。

## 写完必做

1. 在 `docs/README.md` 目录表加一行（日期/主题/一句话）；
2. `git add docs/ && git commit`（消息格式 `docs: <主题>`）并推送；
3. 回复用户时提一句新增记录的路径。

## 边界

- 一行修掉的 trivial 问题（拼写/路径手误）不记录；
- 记录写事实与数据，不写叙事吹嘘；每个"从结果学到什么"必须是可复用的约束或方法，
  不是空话。
